# game-radar · 四国免费游戏榜新游台账

每天两次抓取美国、中国、日本、韩国 App Store 免费游戏榜 Top 100，把第一次进榜的产品整理成台账。产出是三页可直接打开的静态站点、一个 SQLite 面板、一份 14 天分析报告。

---

## 这个项目解决什么问题？

榜单每天在变，但 Apple 只提供当前快照，没有历史接口。想知道某个榜日有哪些新面孔、这些新面孔是什么游戏、后来还在不在榜，只能自己把每天的数据存下来。

存下来之后还有两层障碍：榜单给的是产品名和名次，不解释玩法；四国店面的商店介绍分别是日、韩、英、中文，中文读者看不懂其中相当一部分。逐个点进商店页能把信息补齐，但没法按天回看，也没法和其他市场并排比。

台账里同时列出：当天/当周第一次进榜的产品清单，每个产品的玩法一句话、玩法类型、中文译名、品类和上架天数，以及上一榜日进来的产品现在还在不在榜。

## 为什么选择这个问题？

数据公开、免费、无需授权，且每次抓取都能落盘对账。商业监测工具也有类似看板，但底层数据和判定口径不打开，读者无从核对；用公开榜单做，每个数字都能追到一条 SQL。

首次进榜要排除面板起点已在榜的产品（左删失）；在榜时长有右删失，只能报「已存活 ≥ N 天」；同一 UTC 榜日抓两次、后一次覆盖前一次；累计评分人数、上架日期、品类都是分店面字段，同一产品在不同国家取值不同。这些不先定义清楚，页面上的数字就会悄悄变。

还有一层信息规则做不了：把多语种商店介绍压缩成一句中文玩法、归一个玩法类型、给一个译名，需要翻译和概括。模型输出直接落在卡片上，有明确的使用位置。四国按市场切分也有实际意义——同一款游戏在不同店面的名称、描述、品类归属经常不一样。

## 使用了什么数据、技术和分析方法？

**数据**

| | |
|---|---|
| 来源 | Apple 公开接口：`itunes.apple.com/{cc}/rss/topfreeapplications/limit=100/genre={gid}/json` 取榜单，`lookup?id=...&country={cc}&entity=software` 取详情 |
| 范围 | 四国 × 免费游戏榜 Top100 × 每 12 小时一次 |
| 面板 | 截至 2026-11-07，连续 16 个榜日（10-23 → 11-07），6,400 条榜位记录，524 个产品、675 条「产品 × 店面」记录，缺日 0 |
| 字段 | 名次、产品 ID、名称、品类数组、上架/更新日期、累计评分人数与均分、价格、商店介绍、截图 URL |
| 存储 | SQLite（WAL）：`fact_rank` 榜位、`fact_metric` 按榜日的评分快照、`dim_app` / `dim_app_country` 产品与店面维度、`fact_tag` 标签、`job_log` 抓取记录 |

同日两次抓取后者覆盖前者，`job_log` 记录每次快照时间，引用数字时一并带上版本。

**技术**

Python 3.10+，只用标准库，无需安装依赖。采集、视图计算、页面生成、校验都是本地脚本。

模型部分只调 `deepseek-chat` 的 `chat/completions`：输入产品名与该店面商店介绍（截前 2,200 字），一次调用产出玩法一句话（≤40 字）、玩法类型短语（≤12 字，如「三消+家装」「水排序」）、中文译名；日韩介绍另有单独的译文脚本。生成结果写进 `fact_tag`，附 `descr_country` / `descr_sha1` 记录依据的是哪国、哪份描述；同一份描述不重复生成，人工标签不被覆盖，写不出就留空。

站点由 `build_site.py` / `build_weekly.py` 生成内联 CSS 的 HTML，无外部 JS、无 CDN、无运行时服务。

**分析方法**

- 「首次进榜」定义为产品在可观测窗口内第一次出现在该市场 Top100；面板起点已在榜的按左删失排除，可观测窗口 = 总天数 − 1。
- 品类走 `dim_genre_map`，按 `genres` 数组顺序取第一个非顶级命中项，四国返回值归一到同一套中文名；上游只给顶级类的记为 `Unclassified` 并单列。
- 结构对比只用榜位份额（占了几个位子）。累计评分人数不作为规模代理，日增只走按榜日存的 `fact_metric`。
- 留榜用固定暴露期 cohort，区分「D+7 连续在榜」与「第 7 天当天在榜」。
- 所有报告数字带 `snap_date <= cut` 截点；`verify_numbers.py` 把每个数字翻成一条 SQL 重算比对，当前 129 项断言。
- 口径定义与已知陷阱集中在 `metrics.md`，14 天报告的 14 条限制写在正文末节。

## 实际完成了什么？

**采集与面板**：定时任务每 12 小时跑一次，顺序是采集 → 生成中文标签 → 健康检查 → 告警 → 重建三页。同一榜日重跑覆盖，不产生重复行；`health.py` 查缺日与分店面记录完整性，`check_alerts.py` 覆盖六类运行异常并以退出码标示。

**三页静态站点**（`site/`，自包含，双击即可打开）：

| 页面 | 内容 |
|---|---|
| `index.html` | 当日榜：首次进榜、上次进榜产品的名次变化、当前榜单构成（上架时长分布、品类席位前 5） |
| `yesterday.html` | 前一榜日的同一套结构，按该榜日截点重算 |
| `weekly.html` | 最近一个 7 榜日齐全的已结束自然周：本周首次进榜、进榜名次分布、与上周对照、口径 |

日报与周报的首次进榜清单都按上架时长分组。日报各组默认展开；周报只展开「新上架（≤30 天）」，并在这一组内按首次进榜市场再分四段，其余组折叠。每张卡片常显玩法一句话、玩法类型、中文译名、品类、上架天数、厂商与进榜名次，展开可看商店介绍原文、日韩介绍的中文译文和首张截图。周报按产品去重，同一款跨多国进榜只列一次。

**标签**：当前 `play_desc` 283 款、`like_of` 220 款有值、`name_cn` 176 款、`descr_cn` 120 款。玩法类型允许留空。

**分析与校验**：14 天定版报告 `reports/2026-11-06_v3.md` 及一页摘要；`sql/01–07` 七个可复现查询（面板缺口、榜位变动、评分日增、品类份额、分层、年龄结构、留榜 cohort）与 `results/` 的 CSV 快照；`verify_numbers.py` 129 项数字断言；`tests/` 两组口径与标签回归测试。

## 得到了什么结果？

以下来自 14 天定版报告（窗口 2026-10-23 → 11-05，5,600 条榜位事实，479 个在榜产品，快照 `2026-11-06T04:33:46`）：

- 229 次首次进榜，去重 198 款产品。日本 73 次、韩国 71 次、中国 46 次、美国 39 次。182 次（79.5%）首日就在 50 名开外。
- 固定暴露期的 143 条 cohort 里，D+7 连续在榜 23.8%，第 7 天当天在榜 48.3%。相差的 24.5 个百分点是 35 条掉出后又回来的产品——「还在不在」和「站没站住」是两件事。
- Puzzle 在美国、日本、韩国占 44% / 40% / 36% 的席位；中国是 Action 占 19 席。

当前台账（16 个榜日）累计 257 条首次进榜事件、223 款去重产品。最近一个完整自然周（10-26 → 11-01）98 款，其中新上架 28 款、进榜前 30 位 19 款。

## 这些结果有什么价值，又有哪些局限？

一个连续 16 个榜日、缺口为 0 的面板，是 Apple 不提供的历史视图。判定口径写进了 SQL 和 `metrics.md`，页面与报告里的数字能逐条重算；标签带生成依据的描述哈希，出错能追到是哪份商店介绍。三页站点不依赖后端，可直接分发或挂静态托管。

局限是数据本身决定的：

- 只有免费榜 Top100，榜外新品不可见；Apple 不公开榜单算法，名次是结果不是原因，不能反推下载量、收入或用户规模——项目里没有这些字段。
- 缺一天无法回补，Apple 没有历史接口，每 12 小时抓两次是为了防止缺日。
- 在榜时长右删失；「留存」只指榜位留存。39.7% 这类混合暴露期比例偏高，不能当留存率用。
- 面板 14 天，只有 k≤7 的 cohort 有完整观察窗；同日两次抓取后者覆盖，跨期比较先对齐快照版本。
- 玩法、玩法类型、译名和译文由模型生成，依据的是商店介绍本身；商店介绍缺玩法信息或写得含糊时，输出也会含糊或留空，没有逐条人工核对。
- 品类来自 Apple 的 `sub_genre`，与「玩法」不是一套粒度，两者不能平移比较；`Unclassified` 是上游数据缺失，不是零。
- 定版报告 §3 的累计评价份额与品类内 CR4 是存档数字，依赖会被后续抓取覆盖的字段，不参与可复现校验；站点三页不使用这两个指标。
- `verify_numbers.py` 当前 129 项断言有 2 项不一致，都是标签覆盖数随每日回填增长；报告期望值定版于 11-06。

## 项目能否运行、复现或演示？

**演示**：直接打开 `site/index.html`、`yesterday.html`、`weekly.html`，三页互相链接，无需启动服务、无需密钥。

**运行**：Python 3.10+，无需 `pip install`。数据库 `data/radar.db` 按 `.gitignore` 不入库，新环境需从 `schema.sql` 建库后开始采集；Apple 没有历史接口，已有的 16 个榜日无法在新环境回补，只能从当天重新积累。模型能力可选，把 `.env.example` 复制为 `.env` 填入 key 即可启用，没有 key 时台账、页面、分析照常生成，只是卡片缺玩法、玩法类型、译名与译文。

```bash
python scripts/fetch_daily.py                 # 抓四国 Top100 + 详情，同日重跑覆盖
python scripts/gen_cn_blurb.py                # 生成玩法 / 玩法类型 / 译名（需 .env）
python scripts/gen_descr_cn.py --only-missing # 补翻缺失的日韩商店介绍
python scripts/health.py                      # 缺日与覆盖率体检
python scripts/check_alerts.py                # 六类告警，退出码 1 = 有严重项
python scripts/build_site.py                  # 重建三页
```

**复现与核对**：

```bash
python scripts/verify_numbers.py              # 重算报告数字，129 项断言
python tests/test_kou_jing.py                 # 口径回归
python tests/test_tag_validate.py             # 标签校验 + 变异测试
python scripts/run_sql.py sql/07_cohort_survival.sql   # 跑留榜 cohort 查询
```

`verify_numbers.py` 默认截点 2026-11-05，与定版报告窗口一致。定时任务 `game-radar 每日榜单快照` 每 12 小时执行一次上述链路。

**主要路径**

```
schema.sql        建表与视图，可重复执行
metrics.md        指标定义、公式、口径陷阱
scripts/          采集、标签生成、建页、体检、告警、校验
sql/ results/     七个分析查询与对应 CSV 快照
reports/          定版报告、一页摘要与历史快照
site/             三页静态交付物（入库）
data/radar.db     本地面板（按 .gitignore 不入库）
```
