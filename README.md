# game-radar · 四国免费游戏榜新游台账

每天两次抓取美国、中国、日本、韩国 App Store 免费游戏榜 Top 100，把第一次进榜的产品整理成台账。产出是三页可直接打开的静态站点、一个 SQLite 面板、一份 14 天分析报告。

**项目状态**：可运行。采集与建页链路需本地数据库，三页站点与定版报告可直接查看；标签生成依赖可选的模型密钥。原始库不入库，但仓库带一份 `data/sample/` 样例数据，克隆后能重建面板；在这份样例库上，129 项数字断言有 127 项与报告一致（另外 2 项是标签覆盖数随每日回填增长，见「局限」）。

---

## 这个项目解决什么问题？

榜单每天在变，但 Apple 只提供当前快照，没有历史接口。想知道某个榜日有哪些新面孔、这些新面孔是什么游戏、后来还在不在榜，只能自己把每天的数据存下来。

存下来之后还有两层障碍：榜单给的是产品名和名次，不解释玩法；四国店面的商店介绍分别是日、韩、英、中文，中文读者看不懂其中相当一部分。逐个点进商店页能把信息补齐，但没法按天回看，也没法和其他市场并排比。

台账里同时列出：当天/当周第一次进榜的产品清单，每个产品的玩法一句话、玩法类型、中文译名、品类和上架天数，以及上一榜日进来的产品现在还在不在榜。

## 为什么选择这个问题？

数据公开、免费、无需授权，且每次抓取都能落盘对账。商业监测工具也有类似看板，但底层数据和判定口径不打开，读者无从核对；用公开榜单做，每个数字都能追到一条 SQL。

首次进榜要排除面板起点已在榜的产品（左删失）；在榜时长有右删失，只能报「已存活 ≥ N 天」；同一 UTC 榜日抓两次、后一次覆盖前一次；累计评分人数、上架日期、品类都是分店面字段，同一产品在不同国家取值不同。这些不先定义清楚，页面上的数字就会悄悄变。

还有一层信息规则做不了：把多语种商店介绍压缩成一句中文玩法、归一个玩法类型、给一个译名，需要翻译和概括。模型输出直接落在卡片上，有明确的使用位置。四国按市场切分也有实际意义——同一款游戏在不同店面的名称、描述、品类归属经常不一样。

## 使用了什么数据、技术和分析方法？

**数据**

| | |
|---|---|
| 来源 | Apple 公开接口：`itunes.apple.com/{cc}/rss/topfreeapplications/limit=100/genre=6014/json` 取榜单（`6014` 为 Games 顶级类），`lookup?id=...&country={cc}&entity=software` 取详情 |
| 范围 | 四国 × 免费游戏榜 Top100 × 每天 09:00 / 21:00 各一次（北京时间） |
| 面板 | 自 2026-10-23 起逐日累积，四国 × 免费游戏榜 Top100 × 每天两次；当前规模与完整度（含缺日）写在站点页脚，仓库的样例库冻结在 2026-11-05 截点 |
| 字段 | 名次、产品 ID、名称、品类数组、上架/更新日期、累计评分人数与均分、价格、商店介绍、截图 URL |
| 存储 | SQLite（WAL）：`fact_rank` 榜位、`fact_metric` 按榜日的评分快照、`dim_app` / `dim_app_country` 产品与店面维度、`fact_tag` 标签、`job_log` 抓取记录 |

同一 UTC 榜日的两次抓取（北京时间 09:00 与 21:00）后者覆盖前者，`job_log` 记录每次快照时间，引用数字时一并带上版本。每次抓取按「整份快照」写入：先删本次要写的那段名次再插入，上游返回不全时整班不覆盖、记 `partial` 交告警，不会留下上一班的残行。数据来自公开接口；原始榜位快照存于本地 SQLite，不随仓库分发，可复算的样例见下文。

产品库（`dim_app`）是累计维度，比面板大：当天早些时候抓过、收盘快照里已掉出 Top100 的产品也留在库里，所以产品数总是多于「窗口内出现过的产品数」。

**技术**

Python 3.10+，只用标准库，无需安装依赖。采集、视图计算、页面生成、校验都是本地脚本。

模型部分只调 `deepseek-chat` 的 `chat/completions`：输入产品名与该店面商店介绍（截前 2,200 字），一次调用产出玩法一句话（≤40 字）、玩法类型短语（≤12 字，如「三消+家装」「水排序」）、中文译名；日韩介绍另有单独的译文脚本。生成结果写进 `fact_tag`，附 `descr_country` / `descr_sha1` 记录依据的是哪国、哪份描述；同一份描述不重复生成，人工标签不被覆盖，写不出就留空。

站点由 `build_site.py` / `build_weekly.py` 生成 HTML，样式与脚本内联、不加载外部 JS 或 CSS，也不需要运行时服务；卡片截图来自 Apple 图片服务，离线打开时不显示。

**分析方法**

- 「首次进榜」定义为产品在可观测窗口内第一次出现在该市场 Top100；面板起点已在榜的按左删失排除，可观测窗口 = 总天数 − 1。
- 品类走 `dim_genre_map`，按 `genres` 数组顺序取第一个非顶级命中项，四国返回值归一到同一套中文名；上游只给顶级类的记为 `Unclassified` 并单列。
- 结构对比只用榜位份额（占了几个位子）。累计评分人数不作为规模代理，日增只走按榜日存的 `fact_metric`。
- 留榜用固定暴露期 cohort，区分「D+7 连续在榜」与「第 7 天当天在榜」。
- 所有报告数字带 `snap_date <= cut` 截点；`verify_numbers.py` 把每个数字翻成一条 SQL 重算比对，当前 129 项断言。
- 口径定义与已知陷阱集中在 `metrics.md`，14 天报告的 14 条限制写在正文末节。

## 实际完成了什么？

**采集与面板**：定时任务每天 09:00 与 21:00 各跑一次（北京时间），顺序是采集 → 生成中文标签 → 健康检查 → 告警 → 重建三页。同一榜日重跑覆盖，不产生重复行；`health.py` 查缺日与分店面记录完整性，`check_alerts.py` 覆盖七类运行异常（含「条数与任务记录不符 / 名次不连续」）并以退出码标示。`data/sample/job_log.csv` 是样例库内这 128 次运行的完整记录，可直接核对节奏与成败。

**三页静态站点**（`site/`，HTML 与样式自成一页，双击即可打开；截图需联网）：

| 页面 | 内容 |
|---|---|
| `index.html` | 当日榜：首次进榜、上次进榜产品的名次变化、当前榜单构成（上架时长分布、品类席位前 5） |
| `yesterday.html` | 前一榜日的同一套结构，按该榜日截点重算 |
| `weekly.html` | 最近一个 7 榜日齐全的已结束自然周：本周首次进榜、进榜名次分布、与上周对照、口径 |

日报与周报的首次进榜清单都按上架时长分组。日报各组默认展开；周报只展开「新上架（≤30 天）」，并在这一组内按首次进榜市场再分四段，其余组折叠。每张卡片常显玩法一句话、玩法类型、中文译名、品类、上架天数、厂商与进榜名次，展开可看商店介绍预览（前 320 字，末尾回链 App Store 看全文）、日韩介绍的中文译文和首张截图。周报按产品去重，同一款跨多国进榜只列一次。

**标签**：玩法一句话、玩法类型、译名、日韩介绍译文都按产品存，随每日回填增长；样例库（11-05 截点）里的覆盖是 257 / 196 / 156 / 107 款。允许留空——商店介绍没写清玩法时，模型给的也会含糊，这不影响台账与排期。`like_of` 是历史字段名，当前存的是玩法类型短语而非产品名。

**分析与校验**：14 天定版报告 `reports/2026-11-06_v3.md` 及一页摘要；`sql/01–07` 七个查询与 `results/` 的 CSV 快照（截点 2026-11-05，与定版报告同窗口；`01_gap_check.csv` 只有表头，因为这条查询的正常结果就是 0 行 = 零缺口）——其中 `01/02/03/06/07` 为当前分析，`04` 的评分数份额与 `05` 的四分层已降级为存档、结论不引用（`sql/04_share_cr4.sql:9`、`sql/05_quantile.sql:4-7`）；`verify_numbers.py` 129 项数字断言；`tests/` 三组回归测试，口径回归与快照写入覆盖当前链路，标签校验测试已归档（覆盖 2026-11-06 停用的闭集标签体系）。

**脚本状态**（`scripts/` 共 25 个）：

| 状态 | 脚本 | 说明 |
|---|---|---|
| 当前链路（13） | `fetch_daily` `gen_cn_blurb` `gen_descr_cn` `health` `check_alerts` `build_site` `build_weekly` `new_entrants` `seed_genre_map` `seed_tag_def` `backfill_app_country` `run_sql` `verify_numbers` | 需本地 `data/radar.db` |
| 样例数据（2） | `export_sample` `load_sample` | 导出/重建可公开提交的面板，见下 |
| 一次性迁移（6） | `migrate_tag_v3` `migrate_tag_v4` `migrate_v5*` `apply_golden_v2` | 迁移完即归档，不再运行 |
| 依赖未公开数据（3） | `extract_docx` `make_review_page` `tag_apps` | 分别依赖本地 `refs/`、`tag_work/`，公开仓库内无法直接运行 |
| 实验性（1） | `try_deepseek_search` | 验证 DeepSeek Search 能力，不接生产链路 |

## 得到了什么结果？

以下来自 14 天定版报告（窗口 2026-10-23 → 11-05，5,600 条榜位事实，479 个在榜产品，快照 `2026-11-06T04:33:46`）：

- 229 次首次进榜，去重 198 款产品。日本 73 次、韩国 71 次、中国 46 次、美国 39 次。182 次（79.5%）首日就在 50 名开外。
- 固定暴露期的 143 条 cohort 里，D+7 连续在榜 23.8%，第 7 天当天在榜 48.3%。相差的 24.5 个百分点是 35 条掉出后又回来的产品——「还在不在」和「站没站住」是两件事。
- Puzzle 在美国、日本、韩国占 44% / 40% / 36% 的席位；中国是 Action 占 19 席。

台账累计的进榜事件与去重产品随时间增长，当前值在站点首屏。拿定版报告的 14 天窗口看：229 次进榜事件、198 款去重产品；以最近一个完整自然周（11-02 → 11-08）为例，78 款新进榜产品里有 22 款是新上架、14 款进榜即前 30 位。

## 这些结果有什么价值，又有哪些局限？

一份从 2026-10-23 起逐日累积、缺日如实写在页脚的面板，是 Apple 不提供的历史视图。判定口径写进了 SQL 和 `metrics.md`，页面与报告里的数字能逐条重算；标签带生成依据的描述哈希，出错能追到是哪份商店介绍。三页站点不依赖后端，可直接分发或挂静态托管。

局限是数据本身决定的：

- 只有免费榜 Top100，榜外新品不可见；Apple 不公开榜单算法，名次是结果不是原因，不能反推下载量、收入或用户规模——项目里没有这些字段。
- 缺一天无法回补，Apple 没有历史接口，每天抓两次是为了防止缺日。
- 在榜时长右删失；「留存」只指榜位留存。39.7% 这类混合暴露期比例偏高，不能当留存率用。
- 面板 14 天，只有 k≤7 的 cohort 有完整观察窗；同日两次抓取后者覆盖，跨期比较先对齐快照版本。
- 玩法、玩法类型、译名和译文由模型生成，依据的是商店介绍本身；商店介绍缺玩法信息或写得含糊时，输出也会含糊或留空，没有逐条人工核对。
- 品类来自 Apple 的 `sub_genre`，与「玩法」不是一套粒度，两者不能平移比较；`Unclassified` 是上游数据缺失，不是零。
- 定版报告 §3 的累计评价份额与品类内 CR4 是存档数字，依赖会被后续抓取覆盖的字段，不参与可复现校验；站点三页不使用这两个指标。
- `verify_numbers.py` 的期望值定版于 2026-11-06，只有拿冻结在 11-05 截点的样例库才对得齐（129 项里 127 项一致）；本地活库会多出若干项不一致，两类原因：标签覆盖数随每日回填增长；Apple 会改写产品类目（2026-11-09 实测把一款美国区产品品类数组里的 Strategy 去掉，Strategy / Adventure 的历史席位计数随之互换 21→20、15→16、us 4→3）。定版报告里「148 项全部一致」是当时的状态。
- 2026-11-11 整日未采集（当天定时任务没运行，Apple 无历史接口，补不回来），面板自那以后不是严格连续的；站点页脚与 `check_alerts.py` 的 `KNOWN_MISSING` 都写明这一天，其余缺口仍按 CRITICAL 报警。
- 2026-11-08 之前榜位是按名次逐行覆盖写入的，有 4 个（榜日 × 国家）快照的第 100 名沿用当天早些时候那班的数据（清单见 `check_alerts.py` 的 `KNOWN_BROKEN`）。写入口已改为整份替换，这 4 处没有行级来源可分辨，保留原样。

## 项目能否运行、复现或演示？

**演示**：在线版 <https://han-wangze.github.io/game-radar/> 直接可看。离线时双击 `site/index.html`、`yesterday.html`、`weekly.html` 也是同一套页面，三页互相链接，无需启动服务、无需密钥；卡片截图需联网加载，展开卡片可看商店介绍预览，末尾回链 App Store 看全文。

在线版是**最近一次本机构建的快照**，不是实时榜单：采集跑在本机的定时任务里，`.github/workflows/pages.yml` 只做一件事——把 `site/` 目录发布到 Pages，`site/` 更新时才重新部署。

**复现**：仓库带一份 `data/sample/`——8 张表的 CSV 与 `MANIFEST.json`（面板 16 个榜日、6,400 条榜位、快照版本 2026-11-08T05:40:45）。它冻结在 2026-11-05 截点，与每天在长的本地库不是同一个窗口；定版报告也正好落在这个窗口上，所以拿它复算能对上报告。它不含商店介绍原文与截图 URL（版权与体积原因），但统计复算需要的东西齐全：

```bash
python scripts/load_sample.py                        # 按 schema.sql 重建 data/sample.db
python scripts/verify_numbers.py --db data/sample.db # 129 项断言，结果与本地库一致
python scripts/run_sql.py sql/07_cohort_survival.sql --db data/sample.db
```

**运行**：Python 3.10+，无需 `pip install`。数据库 `data/radar.db` 按 `.gitignore` 不入库，新环境需从 `schema.sql` 建库后开始采集；Apple 没有历史接口，已有的历史榜日无法在新环境回补，只能从当天重新积累。模型能力可选，把 `.env.example` 复制为 `.env` 填入 key 即可启用，没有 key 时台账、页面、分析照常生成，只是卡片缺玩法、玩法类型、译名与译文。

```bash
python scripts/fetch_daily.py                 # 抓四国 Top100 + 详情，同日重跑整份覆盖
python scripts/seed_genre_map.py              # 建品类字典；漏了这步 sub_genre 全成 Unclassified
python scripts/seed_tag_def.py                # 标签定义与版本号
python scripts/gen_cn_blurb.py                # 生成玩法 / 玩法类型 / 译名（需 .env）
python scripts/gen_descr_cn.py --only-missing # 补翻缺失的日韩商店介绍
python scripts/health.py                      # 缺日与覆盖率体检
python scripts/check_alerts.py                # 七类告警，退出码 1 = 有严重项
python scripts/build_site.py                  # 重建三页（开着 .publish-on-build 时会顺带推送线上）
```

**线上看板怎么更新**：本机是唯一有数据库的地方，GitHub Actions 抓不到这段历史，所以线上页只能由本机构建后推上去。每日采集跑完 `build_site.py` 时，如果仓库根有 `.publish-on-build` 开关文件，就会调用 `scripts/publish_site.py` 把三页与 README 同步到发布镜像、提交并推送；推送触发 Pages 重新部署。内容没变时（同一天第二次抓取、数据相同只差生成时刻）脚本自己跳过，不制造空提交。`python scripts/publish_site.py --dry-run` 可以先看差异。

**复现与核对**：`verify_numbers.py`、`run_sql.py` 与所有采集/建页脚本都需要一个数据库（本地 `data/radar.db` 或样例 `data/sample.db`）；无库时 `verify_numbers.py` 直接退出（退出码 2）。三个 `tests/` 不依赖数据库，可直接运行。

```bash
python scripts/verify_numbers.py              # 重算报告数字，129 项断言
python tests/test_kou_jing.py                 # 口径回归（当前链路）
python tests/test_snapshot_replace.py         # 快照写入：整份替换 / 不完整不覆盖
python tests/test_tag_validate.py             # 标签校验 + 变异测试（已归档）
python scripts/run_sql.py sql/07_cohort_survival.sql   # 跑留榜 cohort 查询
```

`verify_numbers.py` 默认截点 2026-11-05，与定版报告窗口一致。定时任务 `game-radar 榜单快照 09:00` 与 `game-radar 榜单快照 21:00` 每天各执行一次上述链路（北京时间）。

